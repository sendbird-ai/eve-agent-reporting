# Access artifact vendoring and coordinated updates

The optional access package is tracked by [issue #11](https://github.com/sendbird-ai/eve-agent-reporting/issues/11).
Keep private policies and consumer inventory in caller-owned configuration. These
repository tools supplement the optional baseline checker's declared/installed
version comparison with archive, lock and byte checks. They create no registry,
fleet inventory, deployment claims or automatic consumer edits. The baseline
checker and broader release tools on optional branches were inspected as patterns;
those unrelated stacks are not merged or required here.

## Prepare or reproduce the baseline

Use an isolated checkout of the reviewed source and the exact toolchain. Do not
replace the recorded archive while reproducing it. All upper-case shell variables
below are **caller-supplied absolute roots or approved values**, not defaults for a
particular consumer. Archive paths and manifest paths are relative to those roots.
The tool never downloads, installs, extracts, writes or changes a consumer.

```sh
node --version # v24.22.2
npm --version  # 10.9.2
npm --prefix "$SOURCE_ROOT/packages/access" ci --ignore-scripts
npm --prefix "$SOURCE_ROOT/packages/access" run typecheck
npm --prefix "$SOURCE_ROOT/packages/access" test
# Obtain zod-4.6.7.tgz under ARTIFACT_ROOT using the committed access lock integrity.
# npm pack zod@4.6.7 --ignore-scripts --pack-destination "$ARTIFACT_ROOT"
# Place the already approved access archive under ARTIFACT_ROOT without changing it.
node "$TOOL_ROOT/scripts/access-artifact/prepare.mjs" \
  "$SOURCE_ROOT" "$SOURCE_COMMIT" "$ARTIFACT_ROOT" \
  "$ARCHIVE_RELATIVE_PATH" zod-4.6.7.tgz > "$NEW_BASELINE_PATH"
shasum -a 256 "$NEW_BASELINE_PATH"
```

For this candidate, compare output byte-for-byte with the committed baseline.
Rebuilding and packing a candidate for comparison is allowed in a **new output
directory**; any changed source/hash requires coordinated review, never overwrite.
Preparation requires every runtime dependency to be an exact version, and an
archive for each reachable dependency; it fails closed for unsupported dependency
kinds or graphs the source lock cannot unambiguously authenticate. If the graph
changes, update the tooling/tests as part of review rather than weakening the pin.

The JS API is `prepare({sourceRoot, sourceCommit, artifactRoot, archive,
dependencyArchives})`, exported from `scripts/access-artifact/prepare.mjs`.
`archive` and all `dependencyArchives` are root-relative files. It returns baseline
data and writes nothing. The CLI prints that JSON; shell redirection creates a new
file. Errors are sanitized at the API and CLI boundaries.

## Read-only consumer verification

The supported layout is a standalone npm lockfile v3 installation at a caller's
approved consumer root, with a direct production dependency on a **relative
`file:...tgz`**. For example, owners copy the unchanged archive to
`vendor/agent-access.tgz`, declare
`"@bshaan77/agent-access": "file:vendor/agent-access.tgz"`, then intentionally
update/review their lockfile and run `npm ci --ignore-scripts` with npm `10.9.2`.
The verifier does not perform any of those mutations. Linked folders, workspaces,
external hoisted installs, package aliases, alternative lock formats and registry
fallback for access fail closed. Supply the actual standalone install/lock root;
adding monorepo layouts requires explicit bounded-resolution tests and review.

```sh
node "$TOOL_ROOT/scripts/access-artifact/verify.mjs" \
  "$BASELINE_ROOT" "$BASELINE_RELATIVE_PATH" "$APPROVED_BASELINE_SHA256" \
  "$ARTIFACT_ROOT" "$ARCHIVE_RELATIVE_PATH" \
  "$CONSUMER_ROOT" vendor/agent-access.tgz
# Equivalent script, from the tooling repository:
npm run access:verify -- \
  "$BASELINE_ROOT" "$BASELINE_RELATIVE_PATH" "$APPROVED_BASELINE_SHA256" \
  "$ARTIFACT_ROOT" "$ARCHIVE_RELATIVE_PATH" \
  "$CONSUMER_ROOT" vendor/agent-access.tgz
```

The API is `verify({baselineRoot, baseline, baselineSha256, artifactRoot, archive,
consumerRoot, dependencyPath})` from `scripts/access-artifact/verify.mjs`.
All roots must be absolute caller-approved directories. All other paths must be
canonical relative paths without empty segments, `.`/`..`, backslashes, absolute
prefixes or unsafe characters. `baselineSha256` is mandatory and supplied from
trusted reviewed data, outside consumer task text.

Verification performs no child processes, package-code imports, network requests,
extraction, installs or writes. It requires the pinned Node version. The recorded
npm version describes preparation/install evidence; installed bytes cannot prove
which historical npm executable created them. Owners must record `npm --version`
with their clean-install commands and logs.

The result reports `verified`, source commit, package/version, archive SHA-512/SRI,
approved baseline hash, actual in-root dependency locations/versions and
`deploymentVerified: false`. Failure exits 1 with sanitized output. The API throws
sanitized errors; filesystem/provider messages and caller paths are not exposed.
It does not discover consumers or rewrite their files. Root/files must be quiescent
and protected against concurrent writers during verification; this is a build and
adoption check, not a hostile-filesystem race-proof sandbox or runtime policy guard.

Checks include the supplied archive **and** consumer-vendored copy; exact
package/version/upstream/license; main lock root declaration and installed entry
version, `file:` resolution, integrity, license and dependency edges; every
installed runtime file; and recursive dependency versions, lock origin/SRI and
bytes. Node's standard in-root `node_modules` search order is followed explicitly,
without executing installed code or searching outside the approved root. Both
nested and deduplicated dependencies must match the approved record. Unrelated
application packages are outside this component's file inventory. Unexpected
packages inside this component's nested dependency directories are rejected.

Missing/extra/modified files, extra empty directories, symlinks (even in-root),
hardlinks in tar, traversal, out-of-root manifests, duplicate tar paths, special
files, bundled modules and PAX/GNU extension records are rejected. The bounded
reader accepts regular npm ustar archives only and never extracts their entries.
If an upstream archive format changes, review the reader rather than disabling it.
File SHA-256 authenticates bytes; installed permission bits are not attested.

## Coordinated update and rollback

1. Select one reviewed upstream commit/version and supported dependency graph.
   Record compatibility/versioning decisions and keep private configuration outside
   shared source. Build/typecheck/test with the exact toolchain and source lock.
2. Pack once into a new immutable candidate directory. Run the existing access
   `check:artifact` and public-content checks there; retain their installed behavior
   and declaration evidence. Authenticate dependency archives with the source lock.
   Reproduce the prepared baseline twice and compare bytes. Review metadata,
   license/attribution, source diff, packed content, and whole-archive/baseline hashes.
3. Review one canonical baseline update, fixture lock changes and toolchain changes
   together. If source/runtime/archive bytes change, notify the update coordinator
   and require **every** participating consumer to use that same source/hash.
   Do not silently rebuild or create per-agent copies of the manifest/source.
4. Each consumer owner prepares a separate reviewable diff: unchanged tarball,
   canonical baseline (or reference to its approved tooling revision and hash),
   direct local declaration, intentional lock update, adapter changes only where
   reviewed, and clean install/build/typecheck/tests. No automated consumer edits
   or fleet-wide registry writes occur in these tools.
5. Run the exact read-only verifier separately on every caller-supplied consumer
   root. Record source/archive/baseline hashes, declaration/lock path, toolchain,
   commands/results and independent installed behavior/compatibility evidence.
   A green unrelated suite does not prove integrity. Keep unavailable consumers
   explicitly pending; synthetic fixtures cannot close actual adoption gates.
6. Human reviewers approve source and consumer diffs. Release, publication, merge,
   deployment and enablement are separate authorizations. Live boundary coverage,
   identity, revocation and security acceptance remain separate evidence.

Rollback restores the previous approved immutable artifact, canonical baseline,
declaration and lock together, then repeats clean install and verification. Keep
restricted paths disabled until the restored baseline and host enforcement pass;
never bypass guards or fall back to broader credentials to recover availability.

## Executed evidence and remaining proof

`npm run test:access-artifact` reproduces the committed baseline and uses two
neutral fixtures with committed npm v3 lockfiles. They install the exact tarball
with npm `ci --ignore-scripts`, use application Zod `4.6.6` (nested access
dependency) and `4.6.7` (deduplicated access dependency), resolve
access's Zod `4.6.7` through Node, execute all 92 access tests **per installation**,
compile installed declarations and exercise the verifier CLI. Intentional
archive/manifest/lock/source-metadata/file/path/symlink/tar tampering must fail.
Filesystem hash snapshots establish that successful verification does not write.
Both isolated fixture installs must also pass `npm audit --json` with no reported
vulnerabilities. CI extends the existing access job with the verifier suite, without
publication changes. Record audit results separately from integrity assertions.

For local evidence with an existing recorded archive, the test runner accepts
`ACCESS_TEST_ARCHIVE_ROOT`, `ACCESS_TEST_ARCHIVE` (relative),
`ACCESS_TEST_DEPENDENCY` (absolute Zod archive), `ACCESS_TEST_CACHE`, and optional
`ACCESS_TEST_OUTPUT` (retain synthetic installs/logs). With no overrides it packs
the built access package into a temporary directory and authenticates the exact
Zod archive. Root build and access build/tests must run first. A changed archive
cannot silently pass the committed fixture locks/baseline.

Actual two-consumer paths, installed resolution and clean builds remain pending
owner-supplied evidence. This document and the synthetic tests establish tooling
and candidate artifact behavior only; they do not claim consumer adoption or live
acceptance. Record that final proof in the coordinated acceptance handoff.
